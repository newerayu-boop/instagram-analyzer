# Почему Jarvis не ломается

Главный вопрос новичка: «а он точно будет работать всегда?»

Честный ответ: **любая часть системы когда-нибудь отвалится.**
Telegram потеряет запрос, Supabase уйдёт на обслуживание, у Anthropic
будет перегрузка, у клиента кончатся деньги на балансе.

Стабильность — это не «ничего не ломается». Стабильность — это
**каждая поломка заранее продумана, и на неё есть готовый ответ.**

Ниже — все места, где ломается, и что там стоит.

---

## 1. Восемь мест, где ломается

### ① Telegram шлёт одно сообщение дважды

**Почему.** Telegram ждёт от твоего сайта ответ. Не дождался за
отведённое время — считает, что не доставил, и шлёт снова. И снова.

**Что будет без защиты.** Один вопрос обрабатывается 3 раза. Клиент
получает три ответа. Ты платишь за три запроса. В финансах — трижды
записанный расход.

**Что стоит.** Таблица `jarvis_updates`, где `update_id` — первичный
ключ. Первое, что делает бот: пытается вставить номер сообщения.
Вставка упала с ошибкой «дубликат» — значит уже обрабатывали, выходим
молча.

```js
if (update.update_id && (await mem.isDuplicate(update.update_id))) return;
```

### ② Кто-то узнал адрес вебхука

**Почему.** Адрес `/api/jarvis` открыт в интернет. Его может найти
сканер или бывший сотрудник.

**Что будет без защиты.** Чужие запросы жгут твой баланс Anthropic.

**Что стоит.** Два замка:
- **секрет в заголовке** — Telegram подписывает каждый запрос
  строкой `TELEGRAM_WEBHOOK_SECRET`. Не совпало — `401`, дальше не идём.
- **белый список** `JARVIS_ALLOWED_IDS` — даже настоящий Telegram
  не проведёт чужого человека.

### ③ Один пользователь пишет без остановки

**Что стоит.** Лимит `RATE_LIMIT_PER_HOUR` — считаем сообщения
за последний час, больше 60 не обслуживаем. Плюс месячный лимит трат
в консоли Anthropic — последняя линия обороны, которую нельзя обойти
никаким багом в коде.

### ④ Модель зациклилась на инструментах

**Почему.** Инструмент возвращает ошибку. Модель думает «попробую
ещё раз» — и так по кругу.

**Что стоит.** `MAX_TOOL_STEPS = 6`. Досчитали до шести — прекращаем
цикл и отвечаем текстом. Плюс бюджет времени `TIME_BUDGET_MS`:
перед каждым шагом смотрим на часы.

### ⑤ Отвалилась база

**Что стоит.** **Память необязательна.** Если Supabase не отвечает —
`memory.js` возвращает пустоту, а Jarvis отвечает без истории.
Хуже, но работает. Ни одна функция памяти не может уронить ответ:
запись истории и журнала идёт в фоне и её ошибки только пишутся в лог.

```js
Promise.all([...]).catch((e) => console.error('[jarvis] persist:', e.message));
```

### ⑥ Отвалился Anthropic

**Что стоит.** Три уровня:
1. SDK сам повторяет запрос 3 раза с нарастающей паузой при
   429 и 5xx — большинство сбоев чинятся здесь незаметно.
2. Не помогло — ловим ошибку и переводим её на человеческий:
   «Пропала связь. Повтори через минуту» вместо стека ошибок.
3. Маршрутизатор упал — не падаем, отправляем в `general`.

### ⑦ Модель отказалась отвечать

**Почему.** Встроенные ограничения безопасности. `stop_reason: 'refusal'`.

**Что стоит.** Проверяем это отдельно от ошибок и отвечаем спокойно:
«Не могу ответить на этот запрос, вернёмся к бизнесу». Это не сбой
кода, и в журнал он идёт как успешный вызов.

### ⑧ Функция не успела за таймаут

**Почему.** Сложный вопрос + несколько инструментов + большой контекст.

**Что стоит.** Бюджет времени внутри цикла. Кончился — отдаём
честный ответ «не успел, задай вопрос поуже». Плюс ручка
`JARVIS_EFFORT`: `low` в 2–3 раза быстрее, чем `high`.

**И главное правило:** Telegram всегда получает `200`. Даже когда
внутри всё сгорело. Иначе он зациклит доставку и умножит проблему.

## 2. Принципы, которые делают систему живучей

**Правило 1. Всё, что можно решить кодом, решай кодом.**
Маршрутизация словарём вместо модели — быстрее, дешевле и не может
ошибиться творчески. ИИ только там, где нужно понимание.

**Правило 2. Каждая часть должна уметь отсутствовать.**
Нет Supabase — работаем без памяти. Нет Whisper — просим написать
текстом. Нет маршрутизатора — идём в общий отдел. Система, где
падение одной детали останавливает всё, — не система, а карточный домик.

**Правило 3. Ошибка идёт к пользователю переведённой.**
Клиент не должен видеть `APIConnectionError`. Он должен видеть,
что ему делать: «повтори через минуту».

**Правило 4. Ограничение есть у всего, что повторяется.**
Цикл — ограничен шагами. Время — ограничено бюджетом. Пользователь —
ограничен лимитом. Аккаунт — ограничен суммой.

**Правило 5. Что не записано в журнал — то не существует.**
Через месяц ты не вспомнишь, почему счёт вырос. Таблица `jarvis_runs`
вспомнит.

## 3. Что смотреть каждую неделю

Пять запросов в Supabase → SQL Editor. Пятнадцать минут в неделю.

**Сколько денег ушло и на что:**
```sql
select dept,
       count(*) as vyzovov,
       sum(tokens_in) as vhod,
       sum(cached_in) as iz_kesha,
       sum(tokens_out) as vyhod
from jarvis_runs
where created_at > now() - interval '7 days'
group by dept order by vyhod desc;
```
Смотри `iz_kesha`: если он близок к нулю — кэш не работает,
и ты переплачиваешь за один и тот же промпт.

**Что ломалось:**
```sql
select error, count(*) from jarvis_runs
where ok = false and created_at > now() - interval '7 days'
group by error order by count desc;
```

**Где тормозит:**
```sql
select dept, round(avg(duration_ms)) as sredne_ms, max(duration_ms) as hudshee
from jarvis_runs
where created_at > now() - interval '7 days' group by dept;
```
Больше 25 000 мс в худшем случае — пора снижать `JARVIS_EFFORT`.

**Кто пользуется:**
```sql
select u.name, count(*) as soobsheniy
from jarvis_messages m join jarvis_users u on u.tg_id = m.tg_id
where m.role = 'user' and m.created_at > now() - interval '7 days'
group by u.name order by soobsheniy desc;
```

**Плохие ответы — читать глазами:**
```sql
select created_at, dept, content from jarvis_messages
where role = 'assistant' and created_at > now() - interval '7 days'
order by created_at desc limit 30;
```
Это самое ценное. Пять плохих ответов в неделю → одно новое правило
в промпте. Так Jarvis становится умнее, а не остаётся навсегда таким,
каким его запустили.

## 4. Сколько это стоит и как платить меньше

Считаем на одного активного предпринимателя: ~30 сообщений в день.

| Статья | В месяц |
|--------|---------|
| Vercel | $0 (бесплатного тарифа хватает) |
| Supabase | $0 (до 500 МБ) |
| Claude API | $8–20 |
| Whisper (голос) | $1–3 |

**Четыре рычага экономии, по силе:**

1. **Кэш промпта** — до −90% на постоянной части. Уже включён.
   Проверяется полем `cached_in` в журнале.
2. **Правила вместо модели в маршрутизации** — 8 из 10 сообщений
   сортируются бесплатно.
3. **`JARVIS_EFFORT`** — `low` дешевле и быстрее `high` в разы.
   Ставь `low` для простых сценариев, `high` — когда нужен разбор.
4. **`HISTORY_LIMIT`** — 20 реплик это много. Для коротких диалогов
   хватает 10, и вход дешевеет вдвое.

Чего делать **не надо**: экономить на модели для основного ответа.
Дешёвая модель на месте бизнес-советника даёт общие ответы, и клиент
перестаёт пользоваться ассистентом. Это дороже сэкономленных денег.

## 5. Что делать при обновлениях

Правило простое: **не проверяй новые промпты на живых людях.**

```bash
# 1. поправил промпт в agents.js
# 2. прогнал 5 типовых вопросов
node tools/jarvis-test.js "клиент говорит дорого"
node tools/jarvis-test.js "сколько я потратил в этом месяце"
node tools/jarvis-test.js "придумай 3 идеи для рилс"
node tools/jarvis-test.js "как передать заказы продавцу"
node tools/jarvis-test.js "привет"
# 3. ответы устраивают — коммит и деплой
```

Держи эти пять вопросов как постоянный набор проверки. Прогоняй его
после каждой правки промптов. Три минуты, которые спасают от
«вчера работало, сегодня отвечает ерунду».
