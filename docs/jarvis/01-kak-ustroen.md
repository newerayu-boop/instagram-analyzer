# Как устроен Jarvis. Полная цепочка

Это главный документ. Если прочитать только один — читай этот.

---

## 1. Что такое оркестратор простыми словами

Представь бизнес-центр. На входе сидит **администратор**. Он не юрист,
не бухгалтер и не маркетолог. Он умеет одно: понять, с чем пришёл человек,
и отвести его в нужный кабинет.

За дверями сидят **четыре специалиста**: маркетолог, финансист, операционный
директор, руководитель продаж. У каждого свой стол, свои папки и свои
инструменты. Маркетолог не лезет в кассу, финансист не пишет сценарии рилс.

Ещё есть **архив** — там лежит папка на каждого клиента: чем занимается,
какие цифры, о чём говорили в прошлый раз.

**Jarvis-оркестратор — это администратор.** Он сам не отвечает на вопросы.
Он делает пятнадцать других дел, чтобы ответ получился быстрым, точным
и не стоил как самолёт.

Ошибка новичка — пытаться сделать «одного умного бота, который знает всё».
Такой бот отвечает общими словами, потому что в его голове одновременно
и реклама, и налоги, и найм. Разделение на отделы — это не усложнение.
Это то, из-за чего ответы становятся конкретными.

## 2. Все функции оркестратора

Пятнадцать обязанностей. Первые пять — до того, как включился ИИ.
Это важно: **большая часть надёжности Jarvis живёт вне модели.**

### Блок А. Приём и защита (без ИИ, работает мгновенно)

| # | Функция | Что делает | Что будет без неё |
|---|---------|-----------|-------------------|
| 1 | **Приём** | Ловит сообщение из Telegram | Нечего обрабатывать |
| 2 | **Подпись** | Проверяет секретный заголовок: это точно Telegram? | Любой узнавший адрес тратит твои деньги на API |
| 3 | **Дедупликация** | Помнит номера обработанных сообщений | Telegram при таймауте шлёт заново — один вопрос обрабатывается 3 раза и списывает деньги 3 раза |
| 4 | **Доступ** | Белый список: кого пускаем | Бота найдут посторонние |
| 5 | **Лимит** | Не больше N сообщений в час на человека | Один клиент за ночь сожжёт месячный бюджет |

### Блок Б. Контекст (память)

| # | Функция | Что делает |
|---|---------|-----------|
| 6 | **Профиль** | Достаёт факты: ниша, город, средний чек, команда |
| 7 | **История** | Достаёт последние 20 реплик диалога |
| 8 | **Нормализация** | Голосовое → текст, фото → подпись |

Без 6 и 7 получается «умный незнакомец»: каждый раз заново спрашивает,
чем ты занимаешься. Именно память превращает чат-бота в **своего**
ассистента. Это то, за что предприниматель платит.

### Блок В. Мышление

| # | Функция | Что делает |
|---|---------|-----------|
| 9 | **Маршрутизация** | Решает, какой из четырёх отделов отвечает |
| 10 | **Сборка промпта** | Склеивает: ядро + роль отдела + профиль + история |
| 11 | **Вызов модели** | Отправляет запрос в Claude вместе со списком инструментов |
| 12 | **Цикл инструментов** | Модель просит инструмент → выполняем → отдаём результат → она просит следующий или отвечает |
| 13 | **Ограничитель** | Не больше 6 шагов и не дольше 50 секунд |

### Блок Г. Выдача и наблюдение

| # | Функция | Что делает |
|---|---------|-----------|
| 14 | **Сохранение** | Пишет диалог и новые факты в память |
| 15 | **Журнал** | Записывает: отдел, токены, время, ошибка |

Журнал — то, что новички пропускают, а потом не могут понять, почему счёт
за месяц вырос втрое. В журнале видно: какой отдел самый дорогой, где бот
тормозит, какие вопросы падают с ошибкой.

## 3. Полная цепочка: путь одного сообщения

```
  Предприниматель пишет в Telegram
              │  «потратил 300 тысяч на таргет, что дальше»
              ▼
  ┌────────────────────────────────┐
  │  Telegram Bot API              │  сервера Telegram
  └────────────────────────────────┘
              │  HTTP POST
              ▼
  ┌────────────────────────────────┐
  │  /api/jarvis  (Vercel)         │  ДВЕРЬ
  │  ① секрет совпал?              │
  │  ② не дубль?                   │
  │  ③ в белом списке?             │
  │  ④ не превысил лимит?          │
  │  ⑤ голос → текст               │
  └────────────────────────────────┘
              │
              ▼
  ┌────────────────────────────────┐
  │  ОРКЕСТРАТОР                   │  АДМИНИСТРАТОР
  │                                │
  │  ⑥ достал профиль из базы      │  «магазин цветов, Ташкент,
  │  ⑦ достал 20 последних реплик  │   чек 250 тыс, 2 продавца»
  │                                │
  │  ⑧ МАРШРУТИЗАЦИЯ:              │
  │     правила нашли «потрат»,    │
  │     «тысяч» → ФИНАНСЫ          │  бесплатно, 0 мс
  │     (если бы не нашли —        │
  │      спросил бы Haiku)         │
  └────────────────────────────────┘
              │
              ▼
  ┌────────────────────────────────┐
  │  ОТДЕЛ ФИНАНСОВ                │  КАБИНЕТ
  │                                │
  │  системный промпт =            │
  │    ядро Jarvis      ←кэш       │
  │  + роль финдиректора ←кэш      │
  │  + профиль бизнеса             │
  │                                │
  │  инструменты:                  │
  │    log_money, money_report,    │
  │    remember, add_task          │
  └────────────────────────────────┘
              │
              ▼
  ┌────────────────────────────────┐
  │  ЦИКЛ ИНСТРУМЕНТОВ             │  РУКИ
  │                                │
  │  Claude: «вызови log_money     │
  │           расход 300000»       │
  │       ↓                        │
  │  мы пишем в базу               │
  │       ↓                        │
  │  Claude: «вызови money_report» │
  │       ↓                        │
  │  мы считаем по базе            │
  │       ↓                        │
  │  Claude: пишет ответ текстом   │
  └────────────────────────────────┘
              │
              ▼
  ┌────────────────────────────────┐
  │  ЗАПИСЬ                        │
  │  ⑭ диалог → в историю          │
  │  ⑮ токены и время → в журнал   │
  └────────────────────────────────┘
              │
              ▼
  ┌────────────────────────────────┐
  │  Ответ в Telegram              │
  │  «💰 Финансы                   │
  │   Записал. За август: приход   │
  │   4.2 млн, расход 3.1 млн...»  │
  └────────────────────────────────┘
```

Весь путь занимает **5–15 секунд**. Из них 90% — работа модели,
остальное — база и сеть.

## 4. Три главных решения в этой схеме

### Решение 1. Маршрутизация — сначала правила, потом ИИ

Можно было спрашивать модель на каждое сообщение: «в какой отдел?».
Это работает, но каждый вопрос стоит денег и добавляет секунду.

Мы делаем иначе. Есть список корней слов:
`деньг`, `расход`, `прибыл` → финансы. `рилс`, `реклам`, `контент` → маркетинг.

Правила ловят примерно 8 из 10 сообщений **бесплатно и мгновенно**.
Модель подключается только там, где правила молчат или спорят.

Ещё важнее: **правило не может ошибиться творчески**. Оно либо нашло
слово, либо нет. Модель иногда придумывает несуществующий отдел —
правило физически не может.

> Принцип, который стоит запомнить: *всё, что можно решить кодом, решай
> кодом. ИИ — только там, где нужно понимание.* Это главный секрет
> стабильных ассистентов.

### Решение 2. Инструменты вместо выдумывания

Модель прекрасно пишет текст и **отвратительно помнит цифры**. Если
спросить «сколько я потратил в июле», она с уверенным лицом придумает
сумму. Для бизнес-ассистента это катастрофа.

Поэтому у каждого отдела есть **инструменты** — маленькие функции,
которые лезут в настоящую базу:

- `log_money` — записать приход/расход
- `money_report` — посчитать за период
- `add_lead` / `move_lead` — вести воронку
- `add_task` / `list_tasks` — вести задачи
- `remember` — запомнить факт о бизнесе

В промпте прямо написано: **цифры бери только из инструментов, свои
не выдумывай**. Модель становится не «умным собеседником», а рабочим
местом с доступом к данным.

### Решение 3. Кэш промпта

Ядро Jarvis плюс роль отдела — это примерно 900 слов, которые
**одинаковы в каждом запросе**. Платить за них каждый раз глупо.

Поэтому системный промпт разрезан на два куска:

```
[ ядро + роль отдела ]  ← неизменно, помечено «кэшировать»
[ профиль этого клиента ]  ← меняется, идёт после
```

Порядок нельзя менять местами. Кэш работает как совпадение по началу
строки: если в начало поставить меняющийся профиль — совпадения не будет
никогда, и кэш не сработает ни разу.

Экономия — до 90% на повторяющейся части.

## 5. Из чего физически состоит Jarvis

| Слой | Чем занимается | Наш выбор | Чем заменяется |
|------|----------------|-----------|----------------|
| Канал | Где сидит пользователь | Telegram Bot | WhatsApp, веб-виджет |
| Дверь | Принимает запрос | Vercel-функция `/api/jarvis` | Cloudflare Workers, обычный сервер |
| Мозг | Думает и пишет | Claude Opus 5 | — |
| Сортировщик | Выбирает отдел | правила + Claude Haiku | только правила |
| Память | Помнит всё | Supabase (Postgres) | Google Sheets на старте |
| Уши | Голос → текст | Whisper | ввод только текстом |

Файлы в этом проекте:

```
api/jarvis.js               дверь: приём, защита, ответ в Telegram
lib/jarvis/orchestrator.js  администратор: маршрут, контекст, цикл
lib/jarvis/agents.js        четыре характера (системные промпты)
lib/jarvis/tools.js         руки: функции работы с базой
lib/jarvis/memory.js        архив: обёртка над Supabase
lib/jarvis/telegram.js      рот: отправка сообщений
lib/jarvis/config.js        все настройки в одном месте
lib/jarvis/schema.sql       таблицы для Supabase
tools/jarvis-setup.js       подключить бота к сайту
tools/jarvis-test.js        проверить без Telegram
```

Обрати внимание: **каждый файл знает только про своё**. `telegram.js`
ничего не знает про Claude. `agents.js` ничего не знает про базу. Это
не красота ради красоты: когда что-то ломается, ты сразу знаешь, куда
смотреть, и чинишь один файл, не задевая остальные.
